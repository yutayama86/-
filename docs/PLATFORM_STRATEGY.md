# イバトコ 地域プラットフォーム戦略

> 「茨城の情報を集約し、地域事業者の集客インフラになる」ための設計書。
> 判断基準：5年後に**なくてはならない地域インフラ**になれるか／少人数で大規模運営できるか／継続課金か／全国横展開できるか。

---

## 0. 最重要の結論（先に読む）

イバトコの価値は**記事ではなく、蓄積される「データ資産」**（店舗・地域・人・口コミ・行動）。
そして最大のボトルネックは機能ではなく **“供給（店舗データ＋一次情報）を人力に頼らず大量に集める仕組み”**。

**アーキテクチャの分岐が最重要判断：**

| レイヤー | 役割 | 技術 |
|---|---|---|
| **読む側（SEO媒体）** | 店舗ページ・記事・エリア・まとめ。検索/AI検索で資産化 | **Astro（静的/ハイブリッド）** ← 今のStackが最適。ここは変えない |
| **書く側（SaaS）** | 会員・口コミ投稿・店舗管理・予約・分析・CRM・広告 | **Cloudflare D1(SQLite)＋Workers API＋Access（認証）** を段階導入 |

→ 「静的の速さ・SEO・低コスト」を保ちつつ、動的部分だけをCloudflareのエッジに足す。これで**1〜2人で店舗1万件規模**まで戦える。

## 1. 現在サイトの改善点

- ✅ ブランド/デザイン/コピーは完成度が高い（媒体としては90点台）
- ⚠️ **記事中心**の構造 → **店舗ページ中心**へ重心移動（着手済み）
- ⚠️ 店舗ページが「ペライチLP」→ **検索資産ページ**へ（特徴/FAQ/近隣/構造化データ）※Priority1で実装
- ⚠️ 供給の仕組みがない（全部手作業前提）→ **一括取り込み＋オーナー自己編集**が必要
- ⚠️ 会員・投稿・分析の土台なし → データが貯まらない（後述DB設計）
- ⚠️ 「地名×悩み」等の**集客用まとめページ**がない → 検索流入の主砲が未実装

## 2. 事業成長を考えたUX改善（回遊＝資産の連結）

**基本原則：どのページも“行き止まり”にしない。**

```
記事 → 店舗ページ → 予約/問い合わせ（CV）
      ↘ 関連記事 ↘ 近隣店舗 ↘ 市町村ページ → 地名×ジャンルまとめ → 別の店舗…
```

- 記事末尾に「店舗カード＋近隣＋同ジャンル人気」を必須配置（一部実装済み）
- 店舗ページに「近隣・関連情報」「同市町村の見どころ」導線（実装済み）
- エリアページを**ハブ化**：市町村→ジャンル→まとめ→店舗の面をつくる

## 4. CMS設計（“編集コンテンツ”と“店舗DB”を分離）

- **編集CMS（記事・レポーター）**：git連携の Decap/Sveltia CMS（既に土台あり）。少人数の編集部向け。
- **店舗データベース**：markdownに押し込まない。**構造化データ**として管理：
  - Phase1：`stores.csv`／Googleスプレッドシート → ビルド時取り込み（大量無料掲載を一気に生成）
  - Phase2：**Cloudflare D1** に移行。管理画面＋オーナー自己編集（Access認証）
- **AI記事補助**：取材メモ＋写真 → 下書き自動生成 → 人が校正（“全記事自社制作”を回避）
- **投稿フォーム**：レポーター/店舗が直接入稿 → 承認フロー（editorial workflow）

## 6. SEO / AI検索 戦略

- **主砲＝地名×ジャンル×悩み**：`/area/水戸/cafe/`、`/guide/水戸-デート/`、`/guide/茨城-雨の日/`。
  検索ボリュームの大きい “ローカル×インテント” を面で取る。
- **店舗ページ＝ロングテール資産**：店舗名／地名＋業態。LocalBusiness/FAQ/Breadcrumb構造化（実装済み）。
- **E-E-A-T**：レポーター著者情報（Person/author）、取材日、実体験の明示。AI時代は「誰が行ったか」が価値。
- **AI検索(GEO)**：明快なエンティティ情報＋FAQ＋簡潔な事実回答＋著者帰属＋`llms.txt`。
- **内部リンク設計**：記事→店舗→エリア→ジャンル→まとめ のトピッククラスタ。
- **技術SEO**：静的配信＝高速（Core Web Vitals有利）、sitemap/OGP自動、画像最適化（次段）。

## 7. 収益化導線（人力を増やさない）

   ↓ 自己アップグレード

   ↓

   ↓
地域DX(¥10万〜30万/月) WEB管理・予約・LINE・CRM（テンプレ化/自動化前提）

横断収益：送客課金(予約/問い合わせCV) ／ 高単価アフィリ(住宅・リフォーム・車・転職・ふるさと納税)
        ／ 地域ターゲ広告 ／ 求人 ／ 地域EC

## 8. 5年後の事業モデル

- **1〜2年**：茨城で無料店舗DB 2,000→8,000件、公式店舗 100→500件、レポーター網、集客まとめページで検索流入を作る。
- **3年**：公式1,000件超×¥9,800＝ベースMRR、集客/地域DXの高単価、送客・アフィリ・求人が乗る＝**地域No.1メディア＆店舗DB**。
- **4〜5年**：茨城で確立した「メディア×店舗DB×SaaS」を**パッケージ化して他県へ横展開**（都道府県＝マルチテナント）。API/データ提供、ふるさと納税・移住・観光DXへ。→ **地域OS**として全国ARR積み上げ（ユニコーン路線）。

## 9. 実装（Priority別）

- **P1 店舗ページ資産化** … ✅実装：特徴/FAQ/近隣/口コミ枠/公式バッジ/無料→公式CTA＋LocalBusiness・FAQPage・Breadcrumb構造化。
- **P2 記事詳細強化** … 一部済（店舗CTA/関連）。著者=レポーター表示、目次、CV導線の追強化【次】
- **P3 市町村SEO** … 見どころ/スポット/グルメ実装済。**地名×ジャンル `/area/[muni]/[category]/` を追加**【次の主砲】
- **P4 公式店舗化導線** … ✅無料→公式CTAを全店舗に設置。
- **P5 会員/管理** … Cloudflare D1＋Access で段階導入【Phase2】
- **P6 SaaS化データ構造** … 上記DB設計に沿って stores を構造化データ→DB移行【Phase2】

## 10. さらに成長する追加アイデア

- **AIモデルコース**：条件（子連れ/雨/デート）→ 行程自動生成（店舗DBを活用＝AIの燃料）
- **LINEミニアプリ**：お気に入り/クーポン/予約通知＝リテンション
- **口コミUGC**：ユーザー投稿でコンテンツ供給を自動化（レビュー資産）
- **学生/大学連携レポーター育成**：一次情報の供給網を安く太く
- **ふるさと納税・移住・観光DX連携**：自治体マネタイズ
- **地域インサイトのデータ提供/API**：行動データの二次利用

## ★経営者視点：茨城で圧倒的No.1になるために“不足しているもの”

1. **供給エンジン（最重要）**：店舗データと一次情報を、**人力に頼らず大量・継続的に集める仕組み**。
   - 具体：店舗一括取り込み（CSV/公開データ）→無料ページ量産、オーナー自己編集の動機と導線、口コミUGC、レポーター供給網。
   - これが無いと、SEO/プラットフォームの**フライホイールが回らない**。機能より先にここ。
2. **初期の熱量（Cold Start）**：最初の店舗網とレポーター網、初期トラフィック（SNS×レポーター）。「鶏と卵」を割る初速。
3. **動的基盤の意思決定**：会員・口コミ・分析・課金を載せる**Cloudflare D1/Workers/Accessの導入判断**（壁にぶつかる前に）。
4. **1本の主砲ページ群**：`地名×ジャンル/悩み` のまとめページ。ここが検索の入口＝集客の証明＝営業の武器。
5. **オペレーションのテンプレ化**：取材→記事→SNS→店舗ページ→公式化 を**型化/自動化**（人を増やさず売上を増やす条件）。

> 一言：**「良いサイト」はもう出来ている。次に作るべきは“サイト”ではなく、供給とデータが自動で貯まる“仕組み（オペレーション＋DB）”。** そこに投資できるかが、5年後に地域インフラになれるかの分岐点。
